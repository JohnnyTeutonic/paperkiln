# FP32 GEMM fallback materialization

The CUDA step-resident fast path remains unchanged. When it declines, the FP32 Phase-A/B1 fallback now materializes both input operands before host transposes or uploads. The CPU branch likewise materializes both operands before host GEMM/transposes. Neither runtime setter flushes already-deferred outputs; a public ops::matmul following a device/residency transition could otherwise read old host bytes. No legacy Matrix device::matmul API change is included.

The retained baseline device source is the exact pre-repair public Git blob. CPU evidence uses the actual compiled old/fixed src/device.cpp and public ops::matmul backward closures, with GNU linker wrapping only device::materialize. A separate authority map holds unchanged mathematical values while host backing bytes are poisoned; the real materialize call restores them. All NN/NT/TN/TT forwards and a nonuniform weighted saved-parent backward fail against independent double arithmetic under old source and pass fixed source. Both variants pass fresh-host controls. This is a synthetic CPU authority model, not actual CUDA execution. Original static-library sources consumed by the fixture match the inspected source exactly; details and library hash are retained.

The CPU backward isolate transfers the same saved mathematical values into the synthetic authority map after the forward. Actual CUDA naturally retains those saved operands on device. The prospective actual-L4 harness requires real stale assertions before and after host-only poisoning, and tests active, device-to-CPU and step-residency-off transitions. No runtime model/configuration data changes, threshold relaxation, training quality result or historical CLI invalidation is claimed.

L4_PROTOCOL.json freezes the future thirty-row old/fixed matrix before actual device results. The shell is only the scientific execution leg; root must supply a frozen source packet, build/bootstrap, serial ownership, deadline/cap and full output return through the existing watchdog. No job is admitted or launched. The ordinary active-on fast path must pass in both versions; it is a correctness control, not a measured performance claim.


Reproduce the CPU boundary matrix with `python3 run_cpu_proof.py --library-build EXISTING_BUILD --library-source MATCHING_SOURCE --out NEW_OUTPUT` from this receipt. It verifies all consumed library source hashes before linking and records library/source/test hashes. Local CMake configuration passes; new target compilation was checked by direct equivalent GNU commands against the hash-bound matching existing library, rather than rebuilding unrelated code. The future L4 `check_l4_gate.py` verifies exact inventory, actual-device markers, expected old numerical failures and fixed passes; numerical assertions themselves remain in the C++ harness, so this checker is not an independent numeric replay.
